# ADR-0003: 语法糖放在哪一层

- **状态**: Accepted
- **日期**: 2026-11-12

## 背景

到 2026-11 时，语法糖已经散在三个地方：

| 糖 | 现在住在 |
| --- | --- |
| `~x`（单表达式体） | `Syntax/Parser.Atoms.cs` |
| `(x: int) => …` 的参数守卫 | `Syntax/Lowering.cs`（`PrependGuard`） |
| 行首 `.` / `?.`（续上一行） | `Syntax/Lexer.cs` |
| `?.` / `??` / `??=` | `Syntax/Lowering.cs` |
| 链式比较 `a < b < c` | `Syntax/Parser.Expressions.cs` |
| 下标糖 `xs[1..3)` | `Syntax/Parser.Expressions.cs` 造 `IndexExpr`，`Lowering` 换成 `Slice` |

这些**都对**，但每加一条语法都要重新想一遍"我该写在哪"，想到最后总是照着上一条抄。
链式比较那次被逼出一条判据，它此前只活在注释里；这次写下来。

## 决策

> **改变树形或结合方式 → parser；只换节点种类 → lowering；只影响分词 → lexer。**

三条的依据不同，所以不能合并成一句"能晚做就晚做"：

- **parser 管"这串 token 是什么意思"**。结合方式、优先级、括号边界都在这里定死；
  一旦交出去，树形就是契约。链式比较改变的是"这串 `a < b < c` 是一棵树还是两棵树"，
  只有 parser 知道，Lowering 看到的时候已经晚了。
- **lowering 管"这个节点用别的节点怎么表达"**。`?.` 是"`Map` 加一个 lambda"，
  `x : T = v` 是"检查加赋值"，都是**同一种树换一种写法**，交给 lowering 可以只写一遍。
- **lexer 管"这串字符怎么切"**。行首 `.` 不改变任何语法，只是把"行首的一个点"重新解释成
  "上一行末尾的 `|>`"，再往后的解析器根本看不出区别。

## 判据怎么用

拿不准的时候问：**这个糖需要知道"上下文"才能决定吗？**

- 需要知道"左边那个式子已经是什么形状"（链式比较、`<|` 封右操作数、`|` 的右结合）→ parser。
- 只需要看"这个节点自己"（`?.` 的接收者、`x : T = v` 的类型）→ lowering。
- 只看相邻两个 token（行首 `.`、`??` 后面是不是新行）→ lexer。

## 例外与已知的模糊地带

- **`~x`** 在 parser 里造 `BlockExpr`。它确实是"改树形"（一个表达式变成一块），
  但它是**语法位置**决定的（`~` 这个记号专门表示"这里写的是体"），不是语义折叠。
  归 parser 是对的，不算破例。
- **参数守卫**在 lowering。它看起来像"改树形"（参数表变成 lambda 体开头的一段检查），
  但参数表本身已经解析完了，守卫只是往体里**插语句**——那是 lowering 的活。
- **下标糖**分两半：parser 只造 `IndexExpr`（"取这个位置"是个真节点），
  `[1..3)` 之于 `Slice` 是"两种写法"的问题，留在 lowering。
- **`f a b` 柯里化**在 parser。它改变结合，且没有对应的节点替换。

## 后果

- 新增语法时不必再讨论"放哪"，按判据走；写在 PR/提交信息里一句就够。
- `Lowering` 保持"纯替换"：不引入新的上下文判断，也不做结合性决定。
- 已知代价：`lowering` 里的规则会看到"已经脱糖一半"的树，所以它必须**幂等**
  （对已经脱糖的树再跑一遍结果不变）。这条目前不成立，`ravel ast -s` 的自验
  就是踩在这儿（见 `.scratch/parser-refactor/plan.md` 的已知问题）。
